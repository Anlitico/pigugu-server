## 3. 背景与问题

固件 OTA 上线后,用户在 App 里看到"有新版本"的**唯一途径是设备页的横幅**(有更新才出现,用户得先打开设备页)。缺一个**常驻、可主动操作**的入口:

- 用户想知道"我的设备现在跑什么固件版本"→ 没地方看;
- 用户想"主动查一下有没有新版本"→ 只能靠等横幅;
- 入口分散、升级行为各入口各做一遍的风险(横幅一处)。

## 4. 产品目标

| 目标 | 度量口径 |
|------|----------|
| 用户可随时查看每台设备当前固件版本与状态 | 版本中心页覆盖 100% 已绑定设备;单设备/多设备均可用 |
| 用户可主动发起"检查更新" | 检查更新返回三态(已最新/发现新版/升级中),≤10s 出结果或失败提示 |
| 所有升级入口体验一致 | 本页、设备横幅、FCM 点击最终进入同一升级页/状态机(复用 `ota-prd.md §5.4`) |

## 5. 功能需求

### 5.1 入口(定稿:A)

- 「我的」页现有「设置」分组新增一行 **固件版本**(图标 + 副标题"查看 / 检查更新 / 升级"),点击进入版本中心页。
- (备选 B:顶栏设置齿轮 → 下拉菜单"固件版本",评估不采用,留档。)
- 本需求只加**一个**入口;后续如需再放置入口(如顶栏),只做入口跳转,不另建页面。

### 5.2 版本中心页

顶部设备区:多设备各一行(可滑动/列表),单设备直接展示。每行:

| 设备行状态 | 呈现 | 行内操作 |
|---|---|---|
| 已是最新 | 设备名 + 当前版本 Vx + 绿色"已是最新" | 检查更新 |
| 有可用更新(在线) | 高亮:新版 Vx + 更新说明摘要 | [检查更新] [立即升级] |
| 有可用更新(离线) | "设备离线"提示 | [检查更新] [预约升级] |
| 升级中 | 细进度条 + 当前阶段 | 点击进入升级页续看 |
| 上次失败 / 已回滚 | 原因 + [重试] | 重试 = 重新发起 |

- 当前版本展示走 `GET /devices` 已附带的 `firmware` 摘要;进入/刷新时拉最新。
- 行状态与服务端 job 状态机一致(不另造状态)。
- **首屏水合(数据可达性)**:列表摘要只含"是否有可用更新 + 活动任务",**不含失败/回滚终态与更新说明**;这些只在 `GET /firmware` 返回。因此**进页时对"有可用更新"的设备补一次 `GET /firmware`**,该行才能即时显示「上次失败/已回滚」与说明摘要(设备量个位数,可接受)。其余行仅用列表摘要。
- 重复点"预约升级"是幂等的:服务端对仍处 `requested`(未开始)的旧预约会 supersede 并重建,行为一致,无需用户感知。

### 5.3 检查更新(主动刷新)

- 点击行内"检查更新":重新拉取该设备固件摘要 + 在线状态(`GET /devices` 摘要 / `GET /firmware`),短暂 loading 后出三态结果:
  - 已是最新 → 提示"已是最新";
  - 发现新版 → 行内升级说明 + [立即升级 / 预约升级];
  - 已在升级中 → 延续当前进度。
- 失败(断网/服务异常):行内提示、可重试,**不**弹全屏错误。
- 弱网最多转圈 ~10s,超时给失败提示。

### 5.4 升级统一入口

本页的[立即升级/预约升级]、设备卡横幅、升级完成 FCM 点击,最终都进入**同一个全屏升级页**(五段动画/盲窗/失败重试/预约,见 `ota-prd.md §5.4`)与同一套 job 状态机——行为与文案不因入口不同而分叉。

### 5.5 主动呈现边界

- 新版本信息的"主动提示"沿用既有机制:**用户打开 App 时设备页横幅**(`ota-prd.md §5.2/F6`)。
- 本页是**常驻的查看/检查/升级管理入口**,**不引入"发版即系统推送"**,与既有 OTA 产品口径一致(如需系统推送提醒,另行立项)。

## 6. 边界与非功能

- **多设备**:列表逐行;操作只作用于该行设备;升级仍为单设备触发。
- **空态**:无绑定设备 → 引导去设备页配网。**未 OTA 使能旧固件**的识别是服务端数据缺口(区分不了"旧固件没上报过版本"与"OTA 使能但尚未上报"),本版**不专门判定**,兜底:版本从未上报(current 为空)的设备按"有可升级候选"展示、允许操作;点了若设备不响应,升级会走既有超时/重试,不影响其它设备。识别信号留 §10 待定。
- 本页只读展示 + 触发;**不做**固件版本目录浏览/退役(属内部/管理台)。
- 弱网/离线:页面可读,操作给失败提示;升级结果靠既有推送回执。

## 7. 明确不做(Phase2+)

- 批量升级 / 按设备组灰度。
- 发版自动系统推送提醒、自动更新。
- 版本历史/变更日志浏览(依赖服务端暴露版本列表 API,另行需求)。
- 多语言文案。

## 8. 验收场景(草案)

1. 绑 1 台设备且为最新 → 我的 → 固件版本:显示设备 + Vx +"已是最新";点检查更新 → 仍最新。
2. 服务端发布新版本后 → 设备页横幅出现;进版本中心 → 该行高亮新版 + 更新说明;[立即升级] 进入五段升级页并正常完成。
3. 设备离线 → 版本中心该行"[预约升级]";预约后文案"下次联网后自动升级";设备上线自动补升并推送。
4. 升级中进入版本中心 → 该行显示进度,可点进升级页续看;杀 App 不影响,重开恢复。
5. 多设备 → 逐行独立状态与操作;只对目标设备生效。

## 9. 交互原型

- `docs/product-design/ota-firmware-manager-prototype.html`(工作区,评审用):入口 A、设备五态、检查更新各结果、升级/预约/重试操作演示。视觉对齐 App 浅 Indigo。

## 10. 待定项

1. 设备行的"更新说明摘要"来源:`firmware_versions.release_notes`(现有字段,首版是否有足够内容填充)。
2. 是否需要"最近一次检查时间 / 上次升级时间"展示(依赖服务端返回 `last_firmware_report_at` 等,可后续加)。
3. 多设备排序(默认:活跃设备置顶 vs 名称序)。
4. **未 OTA 使能旧固件识别**(见 §6):若需要精确显示"当前固件暂不支持在线升级",需服务端补一个可判定信号(如设备 OTA 使能标记 / `last_firmware_report_at` 存在性);本版不做,走兜底。
5. 入口行是否要"未读/可升级"角标:**明确不加**(主动呈现沿用设备页横幅,见 §5.5)。
